# I/O 멀티플렉싱: select & epoll

## 1. 왜 필요한가 - 블로킹의 벽
블로킹 에코서버(accept + read 루프)엔 두가지 한계가 있다.
- 한계 ①: `accept`가 루프 밖 한 번 뿐 -> 손님 하나 끝나면 `return 0`으로 서버가 죽음 -> `while(true)`로 감싸서 해결
- 한계 ②:`read(fd)`가 블로킹이라, 한 손님이 조용하면 서버가 그 `read`에서 잠들어 그 손님만을 기다림 -> 다음 `accept`가 불리지 않음 (다음 손님을 동시에 받지 못함)

즉, "조용한 손님 하나가 서버 전체를 인질로 잡는"구조.

## 2. 멀티플렉싱의 발상
- "특정 한 명을 기다리지 않고, 커널에게 '지금 준비된 fd가 누구냐'를 물어서 준비된 것만을 처리한다."
- 특정 read에서 자는 것이 아니라, 여러개의 fd들을 한꺼번에 감시하는 한 곳(select/epoll)에서 잔다.
- select/epoll 두 함수 모두 잠들고 있다가 준비된 fd가 발생했을 때 깨어나며 각 함수의 return 값을 돌려받는다.
    - `listen_fd`도 감시 대상에 넣는다.
    - '준비됨(readable)' 상태일 때 두개의 함수가 깨어난다고 했는데, `listen_fd`, `client_fd` 각각의 '준비됨'은 아래와 같다.
        - `listen_fd`: accept 대기열에 새 접속이 있다. (누군가가 우리에게 connect 하고자 한다.)
        - `client_fd`: 해당 연결 통로를 통해 데이터가 들어온다. (read 할 것이 들어온다.) / 혹은 해당 통로가 끊긴다. (read가 0 반환)

## 3. select 흐름
- `master`: 감시할 fd 원본 목록(비트맵)
- `read_set`: 매 루프 `master`의 **복사본**. 
    - select 함수에 보내지는 set인데, select는 전달받은 집합(set)을 파괴(변경)해서 반환해주기 때문에 원본인 `master`가 아닌, 복제본 `read_set`을 보내는 것이다.
    - `read_set`에서 '준비 안 된 fd 비트'를 다 꺼버린다.
- `select`: 준비된 것이 있을때까지 대기(블로킹 지점).
- `for` + `FD_ISSET`: 0 ~ max_fd 를 훑으며 준비된 fd가 있는지 체크하고 그 fd들만 처리.
- **블로킹**: 프로세스가 그 함수(여기에서는 select)에서 멈추고 OS가 재운다(CPU 안 씀). 커널이 감시 fd 중 하나라도 준비되면 깨운다. 해당 함수는 그 때까지 리턴하지 않는다.

## 4. select의 약점 3개
- 매 루프 전체 목록을 커널에 복사한다. `read_set = master` -> 복사 비용
- select가 return 해준 set의 0 ~ max_fd 전부를 스캔하며 `FD_ISSET`(비트 켜진 것(=준비된 것) 체크) 한다. max_fd 값이 1만인데 정작 준비된 것이 2개뿐이라면 켜진 2개를 찾기 위해 1만개를 체크하는 꼴.
- 감시할 fd 원본 목록인 master는 타입이 `fd_set`인데, `fd_set`은 FD_SETSIZE(보통 1024) 상한. 그 이상은 담을 수 없다.

## 5. epoll - select의 약점 3개 극복
- 컨셉: 커널에 감시 장부를 맡겨두고, **준비된 것만 받아온다**.
- `epoll_create1(0)`: 커널에 epoll 장부(인스턴스) 생성. 그 장부의 fd(`epfd`)를 반환. '0'은 '옵션 없음'을 가리키는 flags. 일반적으로 `listen_fd`가 3번, 그 다음인 `epfd`가 4번이 된다.
- `epoll_ctl(epfd, ADD/MOD/DEL, fd, &ev)`: 감시 목록(epfd)에 fd를 등록/수정/삭제. 등록은 한 번만 하며, 커널이 해당 목록을 계속 보관하고 관리한다.
- `epoll_wait(epfd, events, 64, -1)`: 감시 목록(epfd)에서 **준비된 것만** `events[]`에 채우고 그 개수(int n)를 반환한다. 여기서 세번째 인자(64)는 배열(events)의 크기, 네번째 인자(-1)는 **무한 대기**를 의미하며, 그 무한 대기로 인해 이 지점이 블로킹 지점인 것이다. 

**select <-> epoll 대응**
- `master`(내 메모리) <-> **감시 목록**(커널 안, `epfd`가 가리킴)
- `read_set`(내가 복사/스캔) <-> `events[]`(커널이 준비된 것만 채워줌)

**장부 내부**(`epfd`가 가리키는 장부): 감시 목록(interest, 등록한 fd 전부) + 준비 목록(ready, 이벤트 난 fd만). 이벤트가 나면 커널이 그 fd를 준비 목록에 자동으로 올리고, `epoll_wait`은 준비 목록만 가져다가 `events[]`에 넣어준다.

**왜 빠를까?**
- 등록은 한 번 뿐 -> 매 루프 재복사 X
- 준비된 것만 `events[]`로 받아 `for(0..n)` 스캔 -> 전체 스캔(0..max_fd)이 없음
- 개수 제한 없음 
=> 할 일이 '준비된 fd 개수'에만 비례한다. 조용한 손님에는 비용이 잡히지 않는다.

## 6. 실전 디테일
- **`DEL` 먼저(장부에서 지우기), `close` 나중**
    - `close`는 시행될 때 감시목록에서 해당하는 fd를 지워준다.
    - BUT, epoll은 fd 번호가 아니라 그 뒤의 **소켓 객체**를 감시한다.
    - `close`의 자동 제거는 **마지막 참조가 닫힐 때만** 일어나서, `dup` / `fork`로 참조가 여럿이면 `close` 하나 했다고 빠지지 않는다(유령 이벤트).
    - fd 번호 재사용 위험도 있다. 해서 명시적으로 `DEL` 먼저 해준 뒤 `close` 해준다.
- **`events[64]`의 64와 n**
    - 64: 한 번에 받을 **최대 개수**
    - 준비된 것이 더 많으면 이번엔 64개, 나머지는 다음 `epoll_wait`에서 받는다. (안 잃음)
    - n: 이번에 실제로 채워진 개수. `for`는 n까지만 순회한다.
- **epfd도 fd**: `epoll_create1`이 fd를 하나 잡아먹어서(예: fd 4), 첫 손님(client_fd)이 4가 아니라 5부터 배정된다. epoll 장부도 다 쓰면 `close(epfd)` 대상

## 7. LT vs ET
`ev.events`에 `EPOLLET`의 on/off로 정해지는 "epoll이 언제 알려주냐"의 차이.

- 우선, epoll_wait이 준비된 fd를 가져올 때, 감시목록의 ready list에 올라와 있는 fd를 받아온다.
- 그리고 해당 fd에 대해 `read`를 요청하면서 `buf`를 같이 보내는데, 소켓버퍼에 담겨있는 해당 데이터는 `buf`의 크기만큼만(우리의 경우 1024) 잘라서 가져온다.

- **LT(Level Trigger, 기본값)**
    - 소켓버퍼에 읽을 데이터가 남아있으면 그것에 대해 계속 알려준다. (해당 fd를 epoll_wait가 반응할 수 있는 '준비상태'를 유지시킨다)
    - 유저가 데이터를 입력한다 -> 소켓버퍼에 담긴다 -> 커널이 감시장부의 ready list에 내 터미널 번호표(fd)를 올린다 -> epoll_wait이 ready list에서 fd를 가져온다(ready list에서 제거) -> 해당 fd의 소켓버퍼를 read 한 후에도 버퍼에 값이 남아 있음을 확인한다 -> fd를 다시 ready list에 올려놓는다.
    - 쉽고 안전하다. 소켓의 블로킹/논블로킹 여부가 상관없다. 어차피 다 읽을때까지 계속 알림을 주고, 각 알림 1회당 read 1회가 발생하기 때문이다. (= read에서 잠들 일이 없음)
- **ET(Edge Trigger, EPOLLET)**
    - 소켓버퍼로 데이터 넘겼으면 알림은 끝이다. 새 데이터가 도착하는 순간(edge)에 딱 한 번만 알림.
    - epoll_wait은 fd를 넘기고 ready list에 올릴지 말지 결정하기 위해 다시 살피지 않는다.
    - 1회 알림에 해당 버퍼를 모두 비워야만한다. 해서 신경 쓸게 많아진다.

**ET가 논블로킹을 요구하는 단계**
1. ET는 한 번만 알림 -> 그 한 번에 버퍼를 다 비워야만 함(drain)
2. read는 한 번에 buf 크기만큼만 -> 여러 번 끊어 읽어야 함 -> `while` 루프
3. while을 멈출 신호가 필요함. 그게 `EAGAIN`(= "이제 없음")
4. EAGAIN을 얻으려면 소켓을 **논블로킹**으로 해야함.

*while문 내부에 소켓버퍼를 read한 결과에 따라 if 분기가 나뉘는데, 소켓버퍼가 비어있으면 read는 아무것도 return 하지 않는다. 여기서 '블로킹' 상태가 발생한다. 그래서 return 값을 `EAGAIN`으로 줌으로써 read의 결과값을 발생시키고, 그로써 if문을 실행시켜 while을 break 할 수 있게하는 것이다. 이 `EAGAIN`을 반환해주는 것이 바로 '논블로킹'이다.

**set_nonblocking 함수**
- `fcntl(fd, F_GETFL)`로 현재 플래그 읽고 -> ` | O_NONBLOCK`으로 논블로킹 비트만 추가 -> `F_SETFL`로 새 플래그로 세팅
- 플래그: 정수의 비트에 담긴 on/off 스위치들. OR(`|`)로 켜고 AND(`&`)로 확인한다. 옵션을 켜느냐 마느냐 하는 것이다.
- 기존 플래그를 보존해야하기 때문에, '기존 플래그 읽기 -> 추가 플래그 더하기 -> 새로 만든 플래그 씌우기'의 순서로 진행한다.

**ET를 쓰는 이유**
- 이벤트당 딱 한 번만 깨워서 **불필요한 epoll_wait 반복/순회를 줄임**
- 특히 EPOLLOUT은 LT면 거의 항상 "쓰기 가능"이라 무한 알림(헛돎)이 발생한다.
- ET를 사용하기 위해, drain(버퍼 다 비우기) + non blocking(EAGAIN 처리)가 필수로 요구된다. 
- ET 사용은 고려해야할 것이 많고 까다롭기 때문에, 단순 서버는 LT(쉽고 안전), 극한 성능(nginx, 게임서버)을 요할 경우에는 ET를 사용한다.

## 8. 테스트로 겪은 것들
`buf[5] + drain 제거 + ET 상태`를 실험

**ET인데 drain 하지 않으면 데이터가 묻힌다**
- "helloworld" 보내면 read(buf[5])가 "hello"만 읽고 종료 -> "world"는 커널 수신 버퍼에 남음.
- ET는 재알림 안 함 -> "world"는 다음 새 데이터(새 edge)가 올 때까지 방치됨.
- 커널 수신 버퍼는 FIFO이라서 나중에 입력 데이터를 전달받으면, 이미 버퍼에 묵혀져있던 "world"가 먼저 나온다.

**SIGPIPE - 끊긴 소켓에 write하면 서버가 죽는다**
- "helloworld" 보내면 위에서 말한것처럼 "hello"만 출력되고 "world"는 버퍼에 남아있다.
- 그 상태에서 해당 커넥션을 끊게되면, 그 자체가 새 edge이기 때문에 '알림'을 유발하고, 그로인해 `read`는 버퍼에 남아있던 "world"를 읽고 `cnt > 0` -> `write`이 호출된다. 
- 문제는, 이미 소켓의 연결은 끊겼는데, 거기다가 write을 보낸 것이다. 이 경우에 커널이 `SIGPIPE`라는 에러를 발생시키고, 해당 에러는 **프로세스를 종료시킨다**. -> 서버 사망
- 방어: main 시작부에 `signal(SIGPIPE, SIG_IGN);` 을 작성해준다. -> 서버가 죽지 않고 write가 `-1`(errno EPIPE) 반환 -> 해당 반환값 받으면 끊김 처리.

**drain 안 하면 fd 누수**
- 마찬가지로 버퍼에 아직 값이 남아있으면 `cnt==0`(끊김) 분기에 도달하지 않는다 -> close/DEL 누락
- ET라서 재알림 없음 -> 버퍼 뒤에 숨은 "끊김(read 0)"을 영원히 읽을 수 없음 -> fd가 열린 채 방치됨(누수)
- 위 상태에서 재접속을 하게되면, fd 5는 재사용하지 못하고 fd 6을 받는다.
