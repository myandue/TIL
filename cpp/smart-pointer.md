# 스마트포인터 (unique_ptr)

## 스마트포인터?
- raw 포인터: `new`를 통해 객체를 생성하면 raw 포인터를 반환해준다. 
- raw 포인터는 delete를 직접 해주어야한다. (`new`를 통해 생성하면 힙 메모리에 저장되기 때문) -> 까먹으면 메모리 누수 및 에러의 위험
- 스마트포인터: 자동 delete (포인터에 RAII 적용)

## unique_ptr (독점 소유)
- 생성: `std::make_unique<T>()` (≈ `new T()` + 자동관리)
- 사용: `p->멤버`, `*p` (raw 포인터처럼 사용)
- 복사: 불가. 이동(move)만 됨. 소유자는 하나. 소유권을 이전시킬 수 있음.

## 소유권 & 수명
- delete 시점: 현재 해당 객체를 소유중인 unique_ptr가, 본인(포인터)이 소속된 스코프를 벗어날 때.
- return: 함수를 호출한 쪽에 소유권을 이동시키며 해당 객체의 수명은 최종 소유자에게 달려있다.

## new vs make_unique
- new: raw 포인터 (직접 delete 필요)
- make_unique: unique_ptr (자동 delete)

## shared_ptr (공동 소유)
- 여러 shared_ptr가 하나의 객체를 공동 소유. (각 포인터 변수가 가리키는 값(주소)은 동일함)
- 복사가 가능하며, 복사를 하게되면 **참조 카운트**가 증가한다.
- 참조 카운트: 소유자(shared_ptr) 수. 이 참조 카운트는 소유자가 소멸할 때 -1이 되며, 0이 될 때(마지막 소유자가 사라질 때) 해당 객체가 delete 된다.
- `use_count()` 로 카운트 확인
- `auto c = b`: 복사(카운트 +1) / `auto& c = b`: 별명(그저 또 다른 호칭 / 카운트 +0)

## unique vs shared
- 기본은 unique
- 여러 곳이 진짜 공유해야할 때만 shared
- shared_ptr를 남발 -> 소유 관계 흐릿 + 카운트 비용 + **순환참조 위험**

## 순환 참조 (shared_ptr 함정)
- 두 객체가 서로를 shared_ptr로 붙잡으면 카운트가 0이 될 수가 없게 된다. -> 영원히 두 객체가 delete 되지 않아 누수 발생
- 외부 접근 통로(지역변수)가 사라졌을 때, 접근은 못하는데 메모리는 점유하고 있는 문제가 발생할 수 있다.

## weak_ptr (순환 끊기)
- 소유하지 않고 **지켜보기만**하는 포인터 -> 카운터를 올리지 않는다.
- 서로를 가리켜야할 때 순환의 한쪽을 weak_ptr로 바꾸면 정상적으로 소멸시킬 수 있다.
- 실제 접근 시 `lock()`으로 잠깐 shared_ptr로 승격

## 소유권 설계
- 순환의 한쪽을 weak_ptr로 변경한다 했는데, 그 기준은 '누가 누구를 소유하냐'이다. (소유한쪽이 shared_ptr)
- 판단 기준:
    - 수명: A가 사라지면 B도 사라져야 자연스럽다 -> A가 소유
    - 포함: B가 A의 일부이다. -> A가 소유
    - 되돌아보기: "내 상위/나를 담은 것"을 가리키는 back-ref -> 본인이 weak
    - 살려두기 테스트: 이 참조 하나로 상대가 계속 살아있는게 괜찮나? -> 아닐경우 해당 참조가 weak
- ex. 게임서버의 경우 '세션이 Player 소유', 'Room/Guild는 사라져도 player가 사라지면 안되기에 weak'
