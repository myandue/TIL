# 멀티스레드: thread, mutex, atomic, condition_variable

## 1. 필요 이유
- 현재 구현한 채팅 서버는 스레드가 하나라서, broadcast 중에 `epoll_wait`으로 돌아가지 못한다.
- 즉, 다른 유저들에게 `write`하고 있을 동안에, 새로운 채팅을 받지 못한다.

## 2. 스레드 
- 스레드는 프로세스 안의 실행 흐름이다. 프로세스가 주소공간과 자원의 단위라면, 스레드는 CPU가 실제로 실행하는 단위다. 한 프로세스 안의 스레드들은 주소공간을 공유한다.
- 스레드마다 스택을 갖고 있으며, 전역·힙·static은 스레드끼리 공유한다. 공유되는 것들이 race 발생 지점이다.
- 스레드는 함수 코드를 따라가면서 스택에 함수를 쌓는다. 
- 스레드 종료는 시작 함수가 반환(스택의 첫 함수가 종료될 때)할 때.
- `t.join()`은 해당 스레드(t)가 끝날 때까지 호출자가 기다리는 것이다.(동기)
- 스레드 생성: `std::thread t(f, a)` - 여기서 a는 함수 f로 보내는 매개변수이다. 

## 3. race condition
- 공통(전역) 자원에 여러 스레드가 접근하게 되면 `race condition`이 발생한다.
- 예를들어 '`counter++` 100만 회 * 2스레드'를 하게되면 2백만이 나와야 할 것 같은데, 매번 다른 값이 된다.
    - `counter++`는 CPU에게 세 단계다. 메모리에서 레지스터로 load -> add -> 메모리로 store
    - t1이 load할 때, t2가 load할 때 둘 다 100이면, 각각이 101을 저장하게 된다. 2가 증가해야하는데 1이 증가하게 되는 것이다.
    - 이것이 lost update

## 4. mutex
- `std::lock_guard<std::mutex> lock(mtx);` 는 해당 줄이 선언된 스코프를 잠근다.
- 즉, 스레드는 해당 lock이 선언된 스코프에 진입할 때 `mtx`를 획득해야 코드를 훑을 수 있는 것이다. 
- 그리고 해당 스코프를 빠져나갈 때 `mtx`를 자동으로 반납해 unlock한다.
- 해당 스코프 내에서 lock을 풀었다가 잡았다가 하려면 `lock_guard`가 아닌 `unique_lock`으로 선언해야한다. 
- `cv.wait`에서 스레드는 잠드는데, 잠들 때 unlock하고 잠든다.(당연하다. 그래야 다른 스레드도 들어와서 잠드니까.) 
    - 그래서 `cv.wait`이 선언된 스코프에서는 lock&unlock이 반복돼야하는데, 그렇기때문에 `unique_lock`으로 선언해야하는 것이다.
- 락 범위가 넓어지면 병렬성이 죽기 때문에, 공유 데이터를 건드리는 최소 구간만 잠그고 I/O나 긴 계산은 락 밖에서 해야한다.

## 5. atomic
- 여러 스레드가 동시에 건드려도 연산이 쪼개지지 않는 변수이다. 점유를 한다거나 특정 값을 보장하는 것이 아니라 말 그대로 '깨지지 않는 값'을 보장한다.
- lock을 잠글 수 없는 상황해서 값이 깨지지 않도록 해야할 때 atomic을 사용한다.
- 예를들어, 종료플래그(bool running)를 관례적으로 atomic으로 둔다. 이유는 시그널 핸들러 안에서는 mutex를 잠글 수 없기 때문이다. 

## 6. condition_variable
- `cv.wait`으로 스레드를 잠들게 해놓고 notify + 조건에 의해 스레드를 깨울 수 있다. 
- `cv.wait(lock, 조건)`의 동작 순서
    1. 락은 쥔 채 조건을 검사한다. 조건이 true이면 통과(다음 코드 수행).
    2. false면 락 해제 및 대기 목록에 등록된채 잠든다.
    3. 외부의 notify에 의해 깨어나면 락을 다시 잡고 조건을 재검사한다.

## 7. 종료 처리
```
running = false; cv.notify_all(); // 끝내라
workers[i].join(); // 끝날 때까지 기다림
```
- 종료플래그를 셋팅하고 `cv.wait`에 notify로 알린다. 
- 스레드들이 종료될 때까지 시간이 소요되기 때문에 그것을 기다린다.
